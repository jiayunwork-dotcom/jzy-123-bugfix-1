# 读模型一致性：增量消费为什么漏事件，以及最终怎么修的

本文记录一次线上对账问题的完整复盘：现象、根因、候选方案对比、最终选择，以及修复为什么在
**服务重启**和**全量重放与写入并发**两种场景下仍然成立。

## 1. 现象

- 40 个初始余额 0 的账户并发开跑；每个账户内部严格串行（一笔等上一笔返回），每笔存 100 分、
  共 25 笔；全部请求 201，无任何错误日志。
- 每个账户版本号都是 26（正确），但有 1~4（压测时甚至 5~9）个账户余额是 2400/2300，
  汇总少几百到上千；偶尔还会**整个账户从读模型消失**（建账户事件被跳）。
- 读模型报告的"已处理序号"等于事件总数，看起来消费完了；做一次全量重放立刻对上，
  序号还是同一个数。单账户串行、测试里一条接一条写永远不复现。

一句话：**增量消费悄悄跳过了已经成功提交的事件，跳过后永远不会补，只有全量重放能纠正。**

## 2. 根因：全局序号的"取号顺序"不是"提交可见顺序"

修复前的消费模型（`accountProjection.ts` 旧版）：

- `events.global_seq` 是 `BIGSERIAL`，值在事务执行 **INSERT 的那一刻**就从序列取走；
  但这行事件要到事务 **COMMIT 之后**才对其它事务可见。
- 增量消费在一个事务里执行
  `SELECT ... FROM events WHERE global_seq > $checkpoint ORDER BY global_seq`，
  把结果逐条应用，然后把检查点更新为本批看到的最大 `global_seq`。

`BIGSERIAL` 的取号顺序与提交顺序**没有任何关系**。两个跨聚合（不同 aggregates 行、互不持锁）
的并发写事务 A、B：

1. A 先 INSERT，取走 seq=100；
2. B 后 INSERT，取走 seq=101；
3. B 先 COMMIT；
4. 此刻投影事务 P 跑增量：`global_seq > 99` 的可见结果只有 `{101}`（A 还没提交）。
   P 应用 101，把检查点推进到 **101**；
5. A 随后 COMMIT，seq=100 的事件**永远落在检查点后面**，再也不会被任何增量消费读到。

这不是"脏读"或快照隔离问题——P 读到的每一行都是已提交的，只是**全局序号空间在它的
一致性快照里有洞**，而检查点机制假定"看到最大序号 N ⇒ 所有 ≤N 的事件都齐了"。这个前提
在跨聚合并发下不成立。

单账户串行不复现，是因为同一聚合的追加被 `aggregates` 行锁串行化，提交顺序天然等于取号顺序；
跨账户才会暴露。压测里"整个账户消失"则是被跳的恰好是 `AccountCreated`，后续存款的
`UPDATE projection_accounts ... WHERE aggregate_id=...` 匹配 0 行、静默不报错。

> 验证：旧代码下用 40×25 并发压测，每轮稳定复现（已保留复现脚本
> `backend/scripts/stress-repro.ts`）。

### 2.1 修复途中还抓到的第二个坑：READ COMMITTED 的"跨语句快照漂移"

第一版修复把消费改成了"按聚合流消费"，但消费事务仍是默认的 READ COMMITTED。压测再次
出现"流位点已到 26、事件一条没应用、检查点照样提交"。原因是 READ COMMITTED 下**每条
语句各自取一个新快照**：

- 语句 1（找落后聚合）看到写事务提交后的 `aggregates.current_version=26`；
- 语句 2（读该流事件）在自己的新快照里却读不到对应事件行（高并发下真实观测到过）；
- 代码信任了语句 1 看到的版本号，直接把流位点写成 26。

**任何"先查版本/元数据、再查数据"的多语句消费，都必须让这两条语句落在同一个数据库快照里。**

## 3. 候选方案与取舍

### 方案 A：写入侧让"全局序号 = 提交顺序"（未选）

做法：所有聚合的追加共用一把全局写锁（例如对一个序号表 `SELECT ... FOR UPDATE` 后再
`nextval`/分配序号），使事务按提交次序拿到全局序号，且序号只在提交点确定。

- 优点：投影侧的全局前缀消费不用改；读模型延迟最低（序号无洞）。
- 代价：**彻底放弃了跨聚合写入的并行度**。不同账户的命令本来互不冲突，现在全局串行，
  写吞吐随账户数下降；且锁要持有到 COMMIT，长事务（批量追加）会放大排队。
- 结论：为了一个读模型的便利，拖垮写模型最有价值的扩展性，不划算。

### 方案 B：消费侧"安全水位"，只越过确定不会再冒出更早事件的位置（未选）

做法：保持全局序号，维护"所有在途追加事务都会预约的区间表"，投影只推进到连续已提交前缀，
洞的位置等对应事务提交或中止再越过。

- 优点：写侧零改动；保留全局顺序消费的语义。
- 代价：实现最复杂——要登记在途事务、识别"洞的主人已经中止"（否则一个中止事务留下的
  洞会让投影永久卡住）、与连接池/事务超时等一堆边界打交道；本质上是在应用层重新实现
  一遍"已提交序号的连续前缀"协调器。
- 结论：复杂度和出错面最大，而收益只是维持一个并不必要的"全局顺序"。

### 方案 C：换消费依据——按聚合流（(aggregate_id, version)）独立消费（**最终选择**）

做法：不再承诺消费全局序号前缀，而是**每条聚合流各自有一个位点**，投影把每个聚合从
"已消费版本"补到"写侧当前版本"。

- 为什么安全：同一聚合的追加被 `aggregates` 行锁串行化，版本号在**提交顺序上严格递增
  且连续**（`UNIQUE(aggregate_id, version)` 兜底）。因此对任何事务快照，"某聚合版本 1..k
  已提交可见"与"events 里存在该聚合 version 1..k 的行"是同一件事，不存在全局序号那种
  跨事务取号/提交错位。流内部永远没有洞。
- 写侧吞吐：**零影响**，追加路径一行不改（全局序号保留，只是不再作为消费边界）。
- 读模型延迟：写后同步跟进仍是一条命令一次增量；多了一次"找落后聚合"的查询，开销可忽略。
- 实现复杂度：一张流位点表 + 消费循环改写；正确性论证局部、可测。

代价（已知、可接受）：

1. 投影不再保证跨聚合事件的消费顺序（A 的 v5 可能先于 B 的 v1 应用）。账户读模型是
   每个聚合独立折叠的，最终状态只依赖各流内部顺序，所以**最终状态逐字段相同**——这正是
   本框架的对账标准。如果未来出现真正跨聚合的投影（跨行转账合并视图），需要的是按命令
   相关的有序消费/关联 ID，而不是 global_seq 前缀（它也解决不了业务因果顺序）。
2. 位点从一个数变成每聚合一行，表规模 = 聚合数，对查询无压力。

## 4. 最终实现

### 4.1 数据结构

- 新增 `projection_stream_positions(projection_name, aggregate_id, last_version)`：
  每条聚合流消费到的版本。幂等迁移，旧库自动兼容（见 4.5）。
- `projection_checkpoints.last_global_seq` **保留**，语义改为"已实际应用事件的最大全局
  序号（高水位）"，同时这一行的 `FOR UPDATE` 行锁承担投影操作的全局互斥。
- 写侧 `events.global_seq`、追加事务、乐观并发控制**完全没动**。

### 4.2 增量消费 `processNewEvents()`

单个 `REPEATABLE READ` 事务内完成：

1. 第一条语句对 `projection_checkpoints` 主行 `SELECT ... FOR UPDATE`——**拍下一致性快照
   并取得全局投影锁，两件事在同一刻发生**；
2. 在该快照内列出落后流（`aggregates.current_version > 流位点`）；
3. 对每条落后流，读出 `version > last_version` 的事件（快照内查询，天然是连续前缀），
   **逐条断言版本连续**（`expected = last+1`，不连续直接抛错回滚，不带空洞前进），
   应用事件、推进该流位点；
4. 高水位取本批事件 `global_seq` 的最大值；读模型、流位点、高水位同事务提交。

为什么是 REPEATABLE READ 而不是 READ COMMITTED：见 2.1，多条读取语句必须共享一个快照。

### 4.3 40001 与排队

高并发的写后跟进会让多个投影调用同时抢那把行锁。REPEATABLE READ 事务里 `FOR UPDATE`
一个"快照之后被前持锁者更新过"的行，PostgreSQL 直接报 **40001（could not serialize
access due to concurrent update）**，而不是阻塞等待。处理方式是教科书式的：
**整个事务回滚后重试**（带指数退避 + 全抖动，上限 100 次）。重试时新事务的快照必在前驱
提交之后，看到的是前驱成果 + 更新的写入，流位点保证不会重复应用。持锁之后投影表只会被
自己修改（别的投影事务在等锁，写事务只写 `events`/`aggregates`），所以 40001 只会发生
在入口排队处，锁内无竞争、无活锁。

### 4.4 全量重放 `replay()`

同样是"单条 RR 事务 + 第一条语句锁检查点行"：锁与切点同一刻取得。然后清空读模型与流位点，
按 `(aggregate_id, version)` 排序重放切点内全部事件，重建流位点和高水位，同事务提交。

**重放与写入并发**为什么成立：

- 重放持锁期间，增量消费在入口排队（40001 重试），不会有投影事务交叉；
- RR 快照之后才提交（或切点时仍在途）的写事务，其事件一律不在本次重放里，也不可能被
  半截应用（快照要么整事务可见、要么整事务不可见）；
- 重放提交后，下一个拿到锁的增量消费在新快照里发现这些流落后，按流补齐——**不丢事件**。
- 写事务之间不需要这把锁：它们只追加 `events`/`aggregates`，与投影表无交集。

### 4.5 服务重启为什么成立

- 流位点与高水位都是**普通持久化表**，崩溃/重启不丢；消费事务是原子的——要么"事件应用
  + 位点推进"一起提交，要么一起回滚，不存在位点越过数据。
- 启动时先执行一次 `processNewEvents()`（只补增量，不全量），重启期间积累的事件自然补齐。
- 旧版本库升级：迁移建出新的位点表（空），`status()` 如实报告落后（已应用 0 条），一次
  写后跟进/启动跟进即补齐，不需要手工干预。
- 另有可关闭的兜底轮询（`PROJECTION_CATCH_UP_POLL_MS`，默认 1s）：任何一次写后跟进失败，
  最迟下一轮自动补齐，而不是等下一次写入或人工重放。

### 4.6 落后必须看得出来

`GET /api/projection/accounts`（以及重放响应）在保留全部旧字段的前提下**新增**：

| 字段 | 含义 |
| --- | --- |
| `eventTotal` | 写侧事件总数 |
| `processedEvents` | 读模型已应用条数（各流位点之和） |
| `lagEvents` | `max(0, eventTotal - processedEvents)` |
| `caughtUp` | `lagEvents === 0` |

追平与否**只按条数判断**，不再看高水位序号——这正是旧 bug 里"序号等于总数却漏了事件"
的假信号来源。跟进失败、写入在途、重放进行中都会表现为 `caughtUp=false`。
`lastProcessedSeq` 保留但仅作高水位展示，不再承诺前缀完整。

## 5. 正确性论证要点（供评审快速检查）

1. **单流前缀完整**：同聚合追加经行锁串行 + 版本唯一约束，任意快照中已提交事件的版本集合
   都是 `{1..k}`。消费只读 `version > 位点` 的行 + 连续性断言，故应用的必是完整前缀。
2. **快照一致**：发现落后、读事件、写读模型、写位点在同一个 RR 事务同一快照内，杜绝 2.1
   的跨语句漂移。
3. **位点不越过数据**：位点值来自实际读到的事件版本，且与读模型同事务提交；失败整体回滚。
4. **互斥**：所有投影消费在检查点行锁上全局串行；重放与增量、增量与增量都不会交叉。
5. **切点封闭**：重放 RR 快照在持锁瞬间确定，切点后提交的事件由后续增量按流补齐。
6. **增量 ≡ 重放**：两条路径都是"每条流各自把版本 1..k 的事件按序 fold 一遍"，fold 是
   纯函数、流间顺序不影响各流行的最终状态，故逐字段相等。
7. **幂等**：消费只从位点之后读；40001 重试基于已提交位点重做，不重复计数。

## 6. 测试

新增 `test/projectionConcurrency.test.ts`（真实 PostgreSQL，`docker compose up -d db`
后 `npm test` 即可在容器/宿主环境运行）：

- 40 账户 × 25 笔、12 账户 × 60 笔并发：**不做重放**，增量读模型与按各账户事件流
  独立 fold 的结果逐字段相同（余额、版本、户主），汇总相同；之后重放结果不变。
- 压测进行中反复触发全量重放：结束后仅靠增量收尾，对账仍然零差异。
- 跟进事务必然失败时：位点不推进、接口 `lagEvents>0 / caughtUp=false`；恢复跟进后补齐。
- "重启"（丢弃内存对象、用同一库重建投影）：位点来自持久化表，重启期间的新事件如实
  显示落后 1 条，一次增量跟进后与独立回放一致。

手工脚本：`backend/scripts/stress-repro.ts`（复现/回归）、
`backend/scripts/stress-replay-during-writes.ts`（重放与写入并发）。

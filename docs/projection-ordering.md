# 增量消费顺序：为什么按 global_seq 会丢事件，以及现在怎么修

## 背景：被稳定复现的丢事件

压测方式：40 个初始余额为 0 的账户并发开跑；每个账户内部严格"上一笔返回再发下一笔"，
每户 25 笔 100 分存款。所有请求 201，写侧每户版本都是 26、合计 1000 条事件。
但读模型里有 1～4 个（极端复现中出现过 10 个）账户余额是 2400/2300，甚至整条账户行
缺失；读模型报告的 `lastProcessedSeq` 与事件总数完全相等，看着像"全部消费完了"。
点一次全量重放，结果立刻正确。串行演示与自带测试从不复现。

## 根因：`global_seq` 的分配顺序 ≠ 提交可见顺序

`events.global_seq` 是 `BIGSERIAL`。PostgreSQL 的序列值在 **INSERT 语句执行时**分配，
而不是事务 COMMIT 时。考虑两个并发的追加事务：

```
T1: INSERT ... 拿到 global_seq = 100，还没 COMMIT（事件对其他会话不可见）
T2: INSERT ... 拿到 global_seq = 101，先 COMMIT（事件可见）

某次增量消费（READ COMMITTED，语句级快照）：
  SELECT ... WHERE global_seq > 99   → 只看到 101，看不到 100
旧的 processNewEvents() 把检查点推进到"本次看到的最大 seq" = 101。

之后 T1 COMMIT，100 永远落在检查点 101 之后 → 被永久跳过，再不会被消费。
```

被跳过的如果是 `MoneyDeposited`，表现为余额少 100、版本却照样往后走（版本是后到的事件
写进去的）；被跳过的如果是 `AccountCreated`，该账户行干脆不存在，后续存款 UPDATE 0 行
（旧代码没检查 rowCount，静默吞掉）。这与观察到的现象完全吻合。

为什么平时不出问题：

- 同一账户串行 / 测试逐条写时，追加事务几乎不重叠，"序号先拿、提交后到"的窗口极短，
  且每条写完立刻同步跟进，消费时通常没有悬而未决的更早序号；
- 40 账户并发把跨事务窗口放大，稳定踩中；
- 全量重放时所有事务早已落定，且在一致快照里读到切点，自然全对。

旧检查点还有个误导性副作用：它推进到的是"见过的最大 seq"而不是"确定连续的位置"，
跳过事件后序号仍然等于事件总数，接口层面看起来已经追平——把"悄悄丢事件"也藏了起来。

## 三个候选修法与取舍

### 方案 A（写入侧）：让全局序号顺序对齐提交顺序

在追加事务里、分配序号之前，取一个全局事务级咨询锁
（`pg_advisory_xact_lock`），把所有聚合的追加在提交顺序上完全串行化。
这样"序号顺序 == 提交可见顺序"，消费侧逻辑几乎不用改。

- 优点：改动小，概念直接，消费端零额外查询。
- 缺点：**抹掉了"不同聚合可以并发写"这一聚合设计的核心吞吐优势**。账户之间本来
  互不相关，却要在全局上排队；账户越多、并发越高，锁竞争越厉害，写延迟随并发上升。
- 不选它：它用牺牲全部跨聚合写入并行度的代价，去满足一个其实只被读模型消费方式
  强加出来的需求。本框架明确演示"不同聚合并发追加互不影响"，不能为读模型牺牲写侧。

### 方案 B（消费侧）：检测序号空洞，只推进到"确定不会再有更早事件冒出来"的位置

继续按 global_seq 消费，但维护"安全水位"：发现空洞不越过，等空洞被填上再前进。

- 致命难点：**已分配但未提交的序号对 `events` 表完全不可见**（READ COMMITTED 下
  根本 SELECT 不到），消费端无法区分一个缺口是"马上会提交的在途事件"还是"事务已
  回滚、序列值永久废弃"。纯靠事件表，只能要么盲目等待（遇到回滚就永久卡死），
  要么维护一张写入登记表 + 清理僵尸登记 + 查 `pg_xact_status` 判定事务结局。
- 缺点：组件最多、最脆弱（登记表要在独立事务里先登记，崩溃后要靠内部系统视图判活），
  读模型延迟受最慢的在途写事务牵制。
- 不选它：复杂度和对 PostgreSQL 内部机制的依赖都最高，收益却只是"继续用一个本来就
  不代表真实顺序的序号做消费依据"。

### 方案 C（换消费依据）：按聚合流（per-aggregate stream）消费 ✅ 采用

不再用全局序号决定"消费什么"，改成**每个聚合各自维护一个"已消费到的版本号"检查点**，
每次把每个流"检查点之后连续的已提交事件前缀"应用掉。全局序号仅保留为对外展示的
保守水位指标，不再参与消费正确性。

为什么它从根上就没有空洞可跳：

1. 同一聚合的追加在写侧已经被 `aggregates` 行的 `SELECT ... FOR UPDATE` 串行化，
   并有 `UNIQUE(aggregate_id, version)` 兜底，因此**每个聚合流的版本号严格连续**
   （1,2,3,…），绝不缺号。
2. 同流内"提交顺序 == 可见顺序"：要提交 v3 必须先拿到该行锁、且 v1/v2 已在之前的
   事务里提交。不可能出现"v3 已可见而 v2 还在未提交事务里"。
3. 所以"从每个流检查点之后开始读"读到的必然是连续前缀；一个尚未提交的同流事件根本
   不会被读到（版本更大的行也还没插入/不可见），检查点只推进到真正应用到的版本，
   下一轮自然补齐。跨聚合之间账户相互独立，消费顺序无关。

代价与权衡：

- 写入吞吐：**零改动、零损失**，不同聚合仍完全并发。
- 读模型延迟：稳态下每次跟进是"查各流头 + 逐流取前缀"，账户很多时是少量带索引的
  集合查询/每流一次小查询；对本框架规模完全够用。
- 复杂度：中等。新增一张每流检查点表、一个投影互斥锁、一个保守水位计算；
  不依赖写入侧任何配合，也不依赖判断事务结局。

## 实现要点（对应 `src/projections/accountProjection.ts`）

1. **`projection_stream_checkpoints (projection_name, aggregate_id, last_version)`**
   记录每个流消费到的版本。
2. **`processNewEvents()`** 单事务内：
   - 取投影互斥锁（事务级咨询锁），与全量重放互斥；
   - 一条 SQL 找出每个流的"下一条待消费事件"（`LEFT JOIN ... IS NULL` 同时覆盖还没有
     检查点行的新聚合）；
   - 逐流从该版本起取全部事件，校验版本连续后应用；
   - 把各流检查点推进到实际应用到的版本；
   - 计算并写入保守全局水位。
3. **存款/取款 UPDATE 检查 `rowCount === 1`**：若账户行不存在，说明消费不变量被破坏
   （理论上按版本流不可能发生），显式抛错并整体回滚，绝不再静默写丢。
4. **全量重放 `replay()`** 持同一互斥锁，在单事务里清空读模型与流检查点、重算；
   切点与事件集用**一条带 `MATERIALIZED` CTE 的语句**在同一快照取得（READ COMMITTED
   下单条 SELECT 用语句开始时刻的快照），避免"先查 maxSeq 再查事件"之间夹入并发提交
   导致切点越过实际读到的事件。
5. **保守全局水位（仅展示用，新增 `latestGlobalSeq / lagEvents / caughtUp /
   laggingStreams` 字段，原 `lastProcessedSeq` 字段名与语义位保留）**：
   - 流内下沿：所有流"版本 > 检查点"的最小 `global_seq - 1`；
   - 在途钳制：通过 `pg_stat_activity.backend_xid` + `pg_locks` 中 events 表上的
     `RowExclusiveLock` 找出"正在写事件且未结束"的事务，水位不超过其中**最早开始的
     事务开始之前已提交的最大 seq**。因为在途事务拿到的任何序号都不会小于这个钳点，
     钳点之前不可能藏着它尚未提交的事件；
   - 持久化时 `GREATEST(旧值, 新值)` 保证水位单调不回退。
   - `lagEvents` / `laggingStreams` 直接对比 `aggregates.current_version` 与每流检查点，
     跟进失败或进程停摆时如实报落后，而不是虚报追平的序号。

## 为什么在两种关键场景下仍然成立

### 服务重启

所有消费状态都在数据库里：读模型行、每流检查点、全局水位都是已提交数据。
重启后内存为空，新实例从检查点继续即可；流检查点的语义是"该版本及之前都已应用并
提交"，未提交的跟进事务会整体回滚、检查点不前移，因此重启后**不重放也不重复应用**。
启动时额外做一次 `processNewEvents()` 自动补齐崩溃期间落下的已提交事件；即便启动补齐
本身失败，API 照常起服，状态接口会明确显示 `caughtUp=false` 与逐账户缺口。

### 全量重放与写入并发

- 增量消费与全量重放由同一个事务级咨询锁互斥，不会出现"重放清空了读模型、而增量
  正在往旧状态上叠事件、重放结束后这些事件被算两次"。
- 重放使用其语句快照：重放进行中**新提交**的事件不在快照里，这些流的检查点按快照内容
  写入；重放一提交，下一次增量跟进就从快照之后的版本继续补齐，既不漏（事件仍在事件流
  里，流检查点没越过它）也不重（重放没应用过它）。
- 重放进行中**尚未提交**的事务同理：事件不可见、不影响切点，提交后由增量补齐。
- 切点（maxSeq）与事件读取在同一条 SQL 的同一快照内完成，切点永远不会越过实际读到
  的事件集合。

## 接口变更

只新增字段，不改动任何路径与已有字段：

`GET /api/projection/accounts`（及 replay 返回体）在原有
`name / lastProcessedSeq / accounts / summary` 之外新增：

| 字段 | 含义 |
| --- | --- |
| `latestGlobalSeq` | 写侧当前最大全局序号 |
| `lagEvents` | 已提交但读模型未消费的账户事件条数（落后即 >0） |
| `caughtUp` | 读模型是否已追平写侧已提交事件 |
| `laggingStreams[]` | 逐账户 `{aggregateId, currentVersion, processedVersion, lagEvents}` |

`lastProcessedSeq` 语义从"见过的最大序号（会虚报）"收紧为"确定完整的安全水位
（提交中有事务时会停住）"，字段名与位置不变。

## 测试

新增 `test/projectionConcurrency.test.ts`（全部打真实 PostgreSQL，可在容器/CI 里随
`npm test` 运行）：

- 40 账户并发 × 每户串行 25 笔，**不做重放**，读模型与逐账户独立回放在
  owner / 余额 / 版本 / 汇总上逐字段相等；
- 加大规模（80 × 40）结论不变；
- 丢弃内存实例、用同一数据库新建投影实例（等价服务重启）后继续并发写入仍一致；
- 压测进行到一半插入一次全量重放，以及重放与写入严格交错并发，终态仍逐字段相等；
- 直接往事件存储写事件、不触发跟进时，状态接口如实报 `caughtUp=false`、
  `lagEvents`、逐账户缺口，水位不虚报；
- 持有一个未提交写事务（占着更小序号）时，水位停在它之前；该事务提交后增量消费
  必然把它补回。

原有 48 个测试全部保持通过。
